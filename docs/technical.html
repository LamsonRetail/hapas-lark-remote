Lark MCP v3 — Remote, multi-user

Một server, một URL, cả công ty dùng chung. Mỗi người đăng nhập Lark của mình và mọi tool chạy đúng dưới danh tính người gọi.

60 tool · REST thuần, không lark-cli · OAuth 2.1 + PKCE · Node ≥22

Đây không phải bản v2 đóng gói lại. v2 là CLI chạy trên máy từng người: mỗi máy một profile, gọi lark-cli bằng cách spawn process, audit ghi vào Bitable. v3 bỏ hết — gọi thẳng REST, không keychain, không profile, không spawn. Một tiến trình phục vụ được cả công ty.

1 · Kiến trúc tổng thể

Điểm khác v2 nằm ở hộp giữa: một tiến trình giữ token của mọi người, thay vì mỗi máy một bản cài.

Vì sao stateless từng request

POST /mcp dựng một McpServer và một transport mới cho mỗi request, rồi đóng lại khi response xong. Tốn vài trăm micro giây, đổi lại không có bất kỳ biến nào sống xuyên qua hai user. Bản v2 giải bài toán này bằng AsyncLocalStorage để "chọn đúng profile"; v3 không cần vì chẳng có gì để chọn nhầm — danh tính đi kèm request, chết theo request.

2 · Trình tự khi một user kết nối

Claude không biết gì về Lark. Nó nói OAuth với server này; server mới đi nói device flow với Lark.

Không cần quyền vào Lark Developer Console. Device flow chỉ cần app_id + app_secret, không cần khai báo redirect URI. Đây là lý do chọn device flow thay vì authorization code flow với Lark.

Hai tầng token, đừng nhầm

TầngAi giữHạnKhi hết hạn
Bearer của server
Claude ↔ server		 Claude access 30 ngày
refresh 180 ngày		 Claude tự gọi /token với grant_type=refresh_token. User không phải làm gì.
Token Lark
server ↔ Lark		 Server, mã hoá trên đĩa access 2 giờ Server tự refresh nhờ offline_access. User không phải làm gì.

Server chỉ lưu hash của bearer, không lưu bản gốc — lộ file cũng không dùng lại được. Token Lark thì mã hoá AES-256-GCM bằng TOKEN_ENC_KEY.

3 · Cái bẫy lớn nhất: refresh token dùng một lần

Bước "đọc lại trạng thái sau khi giành được khoá" là chỗ dễ bỏ sót nhất — thiếu nó thì có khoá cũng vô dụng.

Hệ quả cho việc deploy. Khoá này là mutex trong tiến trình (src/store.js · withUserLock). Chạy hai instance là hai mutex không biết nhau — quay lại đúng kịch bản trên. Muốn scale ngang thì phải chuyển token store sang Supabase với khoá ở DB trước.

Tool là dữ liệu, không phải code

Thêm một tool = thêm một object vào file spec. Chỉ khi cần nhiều hơn một REST call mới phải viết handler.

{
  name: 'calendar_agenda',
  desc: '[CALENDAR] Xem lịch họp của bạn trong khoảng thời gian.',
  schema: {
    start_time: z.string().describe('Unix timestamp giây'),
    end_time:   z.string().describe('Unix timestamp giây'),
  },
  method: 'GET',
  path:   '/open-apis/calendar/v4/calendars/primary/events/instance_view',
  query:  ['start_time', 'end_time'],
}

Endpoint trong các file spec đều bóc từ lark-cli <shortcut> --dry-run của bản zip, nên hai bản luôn gọi cùng một API. Sau khi thêm tool, chạy npm run parity để chắc không lệch với bản zip.

Phân loại tool — vì sao client hỏi lại mãi

Mỗi tool phải được xếp vào đúng một nhóm trong tools/hints.js: chỉ đọc (34), tạo mới (14), phá/gửi (12). Nhóm này thành annotations.readOnlyHint / destructiveHint trả về trong tools/list. Không khai báo thì client buộc phải coi mọi tool là có thể sửa dữ liệu và hỏi xác nhận từng cái — kể cả tool chỉ đọc.

Không suy ra từ HTTP method được. Lark dùng POST cho rất nhiều API tìm kiếm (contact_search_user, drive_search, minutes_search, vc_search). Suy theo method sẽ gắn nhãn "ghi" cho cả một loạt tool chỉ đọc — nên danh sách phải khai báo tay, và assertClassified() ném lỗi lúc khởi động nếu có tool chưa xếp nhóm.

Audit

Chung bảng audit_logs với client zip, phân biệt bằng cột source ('zip' / 'url'). Gom lô 25 bản ghi hoặc 5 giây, bắn nền — tool call không bao giờ phải chờ audit, và audit chết thì tool vẫn chạy.

Thiếu cột thì bỏ cột, đừng bỏ cả lô. PostgREST từ chối nguyên lô khi payload có cột bảng chưa có. Đã mất trắng 100% log của bản remote vì thiếu mỗi error_msg — nhìn bên ngoài vẫn tưởng đang ghi bình thường. Giờ flush() đọc tên cột trong thông báo lỗi, bỏ đúng cột đó rồi gửi lại, và quên sau 30 phút để tự phục hồi khi migration đã chạy.

Canary

Mỗi 60 phút gọi 9 tool chỉ-đọc dưới danh nghĩa CANARY_OPEN_ID, ghi audit với user_name='canary'. Hỏng 2 lần liên tiếp mới DM cảnh báo, và báo đúng một lần cho mỗi lần hỏng — cảnh báo lặp là thứ khiến người ta tắt thông báo rồi bỏ lỡ lần sau.

Vì sao cần khi đã có audit của traffic thật: audit chỉ nói được về tool đang có người gọi. Tool ít dùng mới là chỗ hỏng âm thầm hàng tháng.

-- tool nào bắt đầu lỗi trong 7 ngày qua
select tool_name, lark_code, count(*)
  from audit_logs
 where source = 'url' and ok = false
   and created_at > now() - interval '7 days'
 group by 1, 2 order by 3 desc;

99991663 là user thiếu quyền — chuyện thường ngày. 404 hoặc lỗi tham số mới là dấu hiệu Lark đổi API.

7 · Những chỗ đã trả giá khi dựng

BẫyBiểu hiệnCách tránh
Device flow nằm trên hai host Xin mã ở accounts.larksuite.com, đổi token ở open.larksuite.com. Gọi nhầm trả HTML 404 chứ không phải JSON. JSON.parse chết âm thầm → nay ném LarkError('non_json') kèm 120 ký tự đầu.
Lark nhét chỉ thị cho AI vào payload Trường hint chứa "You MUST…". Trên server dùng chung, response đi thẳng vào context Claude của mọi người. stripInstructions() cắt các trường đó. Phòng thủ tối thiểu, không đầy đủ — nội dung tài liệu/tin nhắn vẫn là dữ liệu không tin được.
Mạng ra Lark chập chờn Đã gặp 5/6 request timeout. Mọi call qua fetchRetry (3 lần, backoff). Poll device flow chịu 8 lỗi mạng liên tiếp trước khi bỏ phiên.
ETag của Express ở endpoint poll Trả 304 cho /authorize/poll — cache một câu "pending" là treo cả luồng đăng nhập. Đặt Cache-Control: no-store cho endpoint đó.
Hai supervisor cùng chạy Tranh cổng 8787, server chết vì EADDRINUSE rồi bật lại vô hạn. Nhìn log tưởng server tự chết. Supervisor gọi /health trước khi khởi động, có ai trả lời thì thoát ngay.
Trùng tên tool MCP chỉ giữ cái đăng ký sau — tool "biến mất" không báo lỗi. tools/index.js ném lỗi ngay lúc khởi động.

8 · Chưa làm

  • Server vẫn chạy trên một máy Windows. Máy ngủ hoặc chưa ai đăng nhập là cả công ty mất kết nối — URL cố định không cứu được. Muốn hết phụ thuộc thì phải deploy, và nhớ pin đúng một instance (xem mục 3).
  • Token store còn là file. Đổi sang Supabase chỉ cần thay readAll/writeAll trong store.js, nhưng khoá per-user phải chuyển xuống DB cùng lúc.
  • /authorize luôn mở device flow mới, kể cả khi user đã đăng nhập trước đó — server không biết ai đang mở trình duyệt. Đặt cookie sau lần đăng nhập đầu sẽ bỏ được bước duyệt lại trên Lark.
  • Diff endpoint với bản zip, không chỉ diff tên tool. Zip cập nhật endpoint theo Lark mà remote thì không — hiện chưa có gì phát hiện ra.
  • Tool phụ thuộc máy user (local_media_transcribe, tải file về đĩa) không port được, giữ ở bản desktop.
